# Каталог ThinkLink и заявки на товары

Данные ThinkLink сохраняются в PostgreSQL. Каталог читает локальную базу, а не обращается к поставщику при каждом открытии страницы.

Цена сайта = цена поставщика в рублях × 1,10, с округлением до копеек. USD/EUR конвертируются по курсам ThinkLink. Неизвестная валюта, отсутствующий курс или неположительная цена не публикуются. Повторный импорт рассчитывает цену заново от цены поставщика.

В каталог попадают доступные товары. Пропавшие из полной выгрузки товары и товары без корректной цены становятся недоступными; исторические позиции заявок сохраняются. Изображения и развёрнутые характеристики в описанном API отсутствуют, поэтому новые карточки пока используют заглушки.

## Подключение

### Автоматическая синхронизация в Docker на проде

Сервис `thinklink-sync` запускается обычной командой `docker compose up -d --build` после готовности PostgreSQL и успешного завершения `migrate`. Если в проекте нет Prisma migrations, `migrate` сначала готовит существующую схему через `prisma/thinklink-upgrade.sql`, затем выполняет `prisma db push`. Скрипт работает и с пустой базой; при конфликтующих категориях создание уникального индекса завершится ошибкой без удаления данных. После подготовки базы `thinklink-sync` берёт настройки ThinkLink из `.env.production`, подключается к той же базе `db`, что и сайт, и сразу выполняет полную синхронизацию. Следующая попытка начинается через час после завершения предыдущей, в том числе после ошибки API. Docker перезапускает завершившийся процесс и поднимает сервис после перезапуска Docker, если сервис не был остановлен вручную.

Перед запуском разрешите внешний IP прод-сервера в ThinkLink и проверьте `THINKLINK_LOGIN`, `THINKLINK_TOKEN`, `THINKLINK_API_BASE` в `.env.production`. Значение `POSTGRES_PASSWORD`, используемое Compose для подстановки из `.env` или окружения, должно соответствовать существующей базе.

```bash
docker compose up -d --build
docker compose logs -f --tail=100 thinklink-sync
```

Сайт запускается независимо от завершения первой синхронизации: в новой базе каталог появится после успешной загрузки. При ошибке импорта транзакция откатывается, ранее загруженные данные сохраняются. Одновременные импорты через сервис и HTTP API защищены блокировкой в PostgreSQL.

### Ручной запуск и разработка

1. В настройках API ThinkLink разрешить внешний IP компьютера разработчика; перед запуском на сервере — IP сервера. При смене IP доступ потребуется обновить.
2. В окружении приложения задать `THINKLINK_LOGIN`, `THINKLINK_TOKEN`, `THINKLINK_API_BASE=https://thinklink.ru/api` и `DATABASE_URL` PostgreSQL.
3. Для разработки параметры БД можно хранить в `.env.local`. Эти файлы исключены из Git и Docker build context. Команды ThinkLink загружают окружение через Next.js; для production задайте `NODE_ENV=production`.
4. При ручном обновлении сначала выполнить `npx prisma db execute --file prisma/thinklink-upgrade.sql --schema prisma/schema.prisma`, затем `prisma db push` с нужным `DATABASE_URL`. В Docker Compose эти шаги выполняются автоматически. Добавлено поле `Order.isInquiry` с безопасным значением по умолчанию `false` для старых заказов. Новые заявки сохраняются с `true`. Категории ThinkLink идентифицируются по источнику, уровню и ID: реальные ответы используют одинаковые ID на разных уровнях. После обновления схемы выполнить полную синхронизацию и `prisma generate`.
5. Выполнить `npm run thinklink:check`. Команда только проверяет доступ, не меняет базу и не выводит учётные данные.
6. Выполнить `npm run thinklink:sync` для полной загрузки. Либо нажать «Обновить каталог» в админке. API также допускает `POST /api/admin/thinklink/sync` с заголовком `x-api-key`, соответствующим `ADMIN_API_KEY`.

`npm run thinklink:watch` загружает каталог сразу и повторяет загрузку через час после завершения предыдущей попытки, пока процесс работает. Для постоянной работы на сервере этот процесс нужно запускать под менеджером служб; сам по себе он не устанавливает расписание. Для долгих загрузок предпочтительна CLI-команда, поскольку HTTP-прокси может ограничивать время запроса.

Синхронизация ограничивает частоту запросов (не более одного за 3,7 секунды внутри процесса). Блокировка PostgreSQL предотвращает параллельные загрузки из нескольких процессов на одну базу. Все изменения применяются в одной транзакции; неполный ответ или ошибка записи откатывает загрузку. Пустая выгрузка каталога/товаров считается ошибкой и не очищает каталог. Максимальное время одной загрузки — 30 минут. Лимиты аккаунта ThinkLink могут также расходовать другие приложения.

## Заявка из корзины

Обязательны имя, телефон, товары и положительные целые количества. Email, компания и комментарий необязательны. Сервер сам рассчитывает предварительную сумму по ценам базы; присланная браузером цена игнорируется. Одинаковые товары объединяются.

Заявка сохраняется в разделе админки «Заявки на товары» со статусом `PENDING`. Остаток поставщика не списывается и не резервируется. Можно запросить количество больше опубликованного остатка: наличие, цену и сроки уточняет менеджер. Передача заказа в ThinkLink и отправка писем не выполняются. Просмотр и изменение заявок доступны только сотрудникам с ролью ADMIN/MANAGER.

## Проверки

`npm run test:thinklink` использует подменённые ответы поставщика и отдельную локальную PostgreSQL `stp_thinklink_test`, указанную в `TEST_DATABASE_URL`. Скрипт очищает только эту специально выделенную тестовую базу. Проверяет цены, иерархию категорий, повторный импорт, снятие недоступных товаров, неполную выгрузку и сохранение заявки без списания остатков.

`npm run type-check` проверяет TypeScript.

При переносе не запускайте seed для существующей базы: текущий seed удаляет данные. Он вынесен в профиль Compose `tools` и больше не запускается автоматически вместе с web.
